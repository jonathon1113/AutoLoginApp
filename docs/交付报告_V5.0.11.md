## 一、两个问题的真实根因

### 1.1 问题一：导入 100 台设备后界面「未响应」

#### 调用链（基于实际代码逐步核查）

```
菜单动作 (appui/main_window.py:591/595)
  └─ on_import_excel()                         ← 旧实现：全部在主线程同步执行
       ├─ QFileDialog.getOpenFileName          模态对话框（正常）
       ├─ openpyxl.load_workbook()              读文件
       ├─ ws.cell(row=i, column=j) 逐格遍历     解析
       ├─ 构造 device 字典 / 分组
       ├─ 重复设备检查、字段格式校验
       ├─ encrypt_devices()  ←── ★ 耗时 99.7%
       ├─ save_devices()  写 devices.json
       ├─ on_refresh()  重新加载设备
       └─ update_device_list() / create_group_buttons()  刷新界面
```

#### 实测耗时（修复前，100 台设备，本机实测）

| 阶段 | 耗时 | 占比 |
|------|------|------|
| `openpyxl.load_workbook()` | 31 ms | 0.2% |
| 逐格 `ws.cell()` 遍历 + 校验 | ~0 ms | ~0% |
| **`encrypt_devices()`（PBKDF2 50000 轮 × 200 字段）** | **13 110 ms** | **99.7%** |
| 其余（写盘、刷新、UI） | ~0 ms | ~0% |
| **主线程合计阻塞** | **13 141 ms** | 100% |

Windows 在主线程连续无响应约 5 秒后即弹出「未响应」对话框，
13.1 秒的同步阻塞必然触发该提示 —— **数据量不是原因，缺少耗时日志才会让人误以为是数据量问题**。

#### 根因结论（两条，均已实测确认）

1. **主线程同步执行了 PBKDF2 密钥派生**。`encrypt.py` 的 `_derive_keys()` 对每个
   username / password 字段各做一次 `hashlib.pbkdf2_hmac('sha256', ..., iterations=50000)`
   （约 65 ms/字段）。100 台设备 = 200 个字段 = 13 秒。这段代码位于 Qt 主线程，
   期间事件循环完全停止，窗口无法拖动、无法响应任何输入。
2. **导入链路缺少任何进度反馈**。旧实现从打开文件到刷新完列表期间，
   `stat_label` / `progress_label` / `progress_bar` 三个已有的进度控件**一个都没有被使用**，
   用户看到的是一个「卡死」的窗口，既不知道在做什么，也不知道还要等多久。

#### 已排除的怀疑项（有证据，不是推测）

- **不是「每导入一台设备就刷新一次整个列表」**。核查 `update_device_list()`：
  是一次性 `clear()` 后逐项 `addItem()`；`create_group_buttons()` 按分组创建卡片。
  **不存在逐设备刷新**。修复前的问题与刷新次数无关。
- **不是 openpyxl 解析慢**。实测解析 100 台仅 32 ms。
- **不是界面控件创建慢**。设备列表是 `QListWidget` 的条目，不是复杂控件。

### 1.2 问题二：`looks_like_password` 误判账号输入框

#### 现场日志对应的真实场景

```
selector = CSS_SELECTOR=input.el-input__inner[type="text"][placeholder="账号"]
结果=角色不符 ... 说明=角色校验未通过, 元素角色与预期不符 (looks_like_password)
```

#### 原始判断条件（修复前 `appcore/element_roles.py`）

```python
def _password_evidence(info):
    """密码正向证据强度"""
    tokens, text = _tokens(info.get('id'), info.get('name'),
                           info.get('cls'),          # ← 类名参与
                           info.get('placeholder'),
                           info.get('aria'))
    if _has_token(tokens, _PASSWORD_TOKENS) or _has_cn(text, _PASSWORD_CN):
        return 2
    return 0

def _judge_username(info, visible, trusted=False, hint=''):
    ...
    if _password_evidence(info) >= 2:            # ← 阈值 2
        return REJECT, 'looks_like_password', 0
```

`_PASSWORD_TOKENS = ('password', 'passwd', 'pwd', 'pass', 'passwrd', 'userpass', 'pwdconfirm')`

#### 为什么一个 `type="text"`、`placeholder="账号"` 的框会被判成密码框

原实现把**五类来源等权处理**，任一命中即返回 2（= 硬性否决）：

| 来源 | 示例 | 原实现权重 |
|------|------|-----------|
| placeholder / aria-label | `placeholder="请输入密码"` | 2（强） |
| **name / id** | `name="password"`、`id="pwd"` | 2（强） |
| **class（CSS 类名）** | `class="el-input__inner password"` | **2（与占位符同权！）** |
| **autocomplete** | `autocomplete="current-password"` | **2（与占位符同权！）** |
| style | `-webkit-text-security` | 2（强） |

同时 `_username_evidence()` **完全不检查 class**，判定是**不对称**的：

```python
def _username_evidence(info):
    tokens, text = _tokens(info.get('id'), info.get('name'),
                           info.get('placeholder'), info.get('aria'))   # ← 没有 cls
```

于是，只要这个账号输入框**自身**携带以下任一线索，就会被硬判 `looks_like_password`：

- 框架给它加了 `class="... password ..."`（很多前端组件库对表单内所有输入框套用同一组类名）；
- 框架给它加了 `autocomplete="current-password"`（浏览器密码管理器的自动填充标记常被模板复制到整组表单）；
- 它的 `name` / `id` 恰好是 `password`；
- 它的 `aria-label` 写着「密码」。

而 `placeholder="账号"` 这条**账号语义**在原实现里**完全无法抵消**上述任何一条线索
（`_username_evidence` 只在别的分支用，不参与冲突消解），所以一旦命中就直接否决。

#### 12 组离线矩阵实测（修复前，用于定位真实触发条件）

| # | 元素属性 | 修复前判定 |
|---|---------|-----------|
| A | `type=text, placeholder=账号, class=el-input__inner` | **ACCEPT** |
| B | A + `autocomplete=current-password` | ❌ **looks_like_password** |
| C | A + `style=-webkit-text-security` | ❌ **looks_like_password** |
| D | A + `name=password` | ❌ **looks_like_password** |
| E | A + `aria-label=密码` | ❌ **looks_like_password** |
| F | A + `id=password` | ❌ **looks_like_password** |
| G | A + `name=passwd` | ❌ **looks_like_password** |
| H | A + `aria-label=password` | ❌ **looks_like_password** |
| I | A + `name=pass` | ❌ **looks_like_password** |
| J | A + `class="el-input__inner password"` | ❌ **looks_like_password** |
| K | A + `placeholder=密码` | ❌ **looks_like_password** |
| L | `type=password` | ❌ **looks_like_password** |

> 结论：**选择器本身（`type="text"` + `placeholder="账号"`）并不足以触发误判**。
> 真正触发的是**被匹配元素自身**携带的 class / autocomplete / name / id / aria 线索。
> 日志只能证明「匹配到的元素被判成密码」，不能证明「选择器写错了」——
> 这正是任务书要求「必须检查实际校验逻辑和元素属性」的原因。

#### 第二个根因：缺少页面级上下文

原实现**没有任何页面级判据**：即使一个输入框同时带「账号」和「密码」语义，
也只会武断地二选一（永远选密码），不会去看页面上是否另有独立的 `type=password` 输入框。
这就导致「账号框与密码框共用 class / autocomplete」的表单必然误判。

## 四、`looks_like_password` 的原始判断条件与误判原因（复述）

### 原始条件

```python
# appcore/element_roles.py（修复前）
_PASSWORD_TOKENS = ('password', 'passwd', 'pwd', 'pass', 'passwrd', 'userpass', 'pwdconfirm')

def _password_evidence(info):
    tokens, text = _tokens(info.get('id'), info.get('name'),
                           info.get('cls'),            # ← 类名与占位符同权
                           info.get('placeholder'),
                           info.get('aria'))
    if _has_token(tokens, _PASSWORD_TOKENS) or _has_cn(text, _PASSWORD_CN):
        return 2                                   # ← 2 即「硬性否决」

def _judge_username(info, visible, trusted=False, hint=''):
    ...
    if _password_evidence(info) >= 2:
        return REJECT, 'looks_like_password', 0
```

### 本次误判的具体原因

账号输入框元素**自身**携带了 class / autocomplete / name / id / aria 之一的密码线索，
而这些线索在原实现里与「placeholder 写着密码」**同权（都是 2 分）**；
同时账号语义（`placeholder="账号"`）在**用户名判定分支中根本没有参与冲突消解**，
因此账号线索无法抵消密码线索 —— 只要命中任一密码线索就直接 `REJECT`。

再加上原实现**没有任何页面级判据**，无法利用「页面上另有独立的 `type=password` 输入框」
这一事实来证明当前元素是账号框。

### 修复后的判定规则（证据分级）

```
密码证据：
  强 2.0  placeholder / aria-label 含「密码 / 口令」
  强 2.0  style 含 -webkit-text-security
  中 1.0  name / id 的精确词元命中（password / passwd / pwd / pass ...）
  弱 0.5  class 含密码词            ← 只算样式名，框架常与账号框共用
  弱 0.5  autocomplete=current-password / new-password  ← 浏览器自动填充标记

用户名证据：
  强 2.0  name / id 精确用户名词，或 placeholder / aria 含「用户名 / 账号 / 帐号 / 邮箱 / 登陆名」
  中 1.0  autocomplete=username / email，或 type=email
  （class 不参与 —— 账号框与密码框的类名常常完全相同）
```

判定流程：

1. **结构性否决优先**（标签 / type / 隐藏 / 只读 / 禁用 / 不可见）—— 与原实现一致，未削弱。
2. **验证码语义优先于密码语义** —— 避免验证码框被当用户名。
3. 密码证据 **≥ 中(1.0)**：
   - 同时有强用户名证据 → **AMBIGUOUS（证据冲突）**，交由页面上下文消歧；
   - 否则 → `REJECT / looks_like_password`。
4. 密码证据仅为**弱(0.5)** → **ACCEPT**，但记录 `weak_password_signal(...)` 提示。
5. 页面级消歧：若冲突且**同一文档内存在独立的 `type=password` 输入框**
   （`locator.first.evaluate("() => document.querySelectorAll('input[type=\"password\"]').length")`，
   evaluate 在元素自身文档上下文执行，iframe 内同样正确），
   则判定「真正的密码框另有其物」，当前文本框按账号处理；
   **页面中没有独立密码框 → 保持冲突，报告歧义，绝不盲填**。

### 避免两种极端（任务书 2.4 的 8 条，逐条落实）

| 要求 | 实现 | 验证 |
|------|------|------|
| `type=text` + `placeholder=账号` 不因通用 class 名被误判 | class 只算弱证据（0.5 < 阈值 1.0） | 矩阵 J / 场景 14 |
| `type=password` 真密码框不被当用户名 | `_effective_type == 'password'` 直接否决 | 矩阵 L / 场景 11 |
| `placeholder="请输入密码"` 正常参与密码识别 | 强证据 2.0 | 矩阵 K |
| `type=text` 实现的密码框仍能识别 | `style=-webkit-text-security` 强证据；模板显式声明（`hint` 含密码语义）时按声明采信 | 矩阵 C / 场景 11 |
| 验证码框不被误判为用户名或密码 | 验证码语义优先；验证码框 `class` 不参与 | `tests/test_element_roles.py` 原有场景全 PASS |
| 登录按钮不被当用户名字段 | `_judge_username` 对非 input/textarea 直接否决；`_judge_button` 反向否决普通输入框 | 原有场景全 PASS |
| 多匹配 / 证据冲突时进一步验证或报歧义 | `accepted` 多个 → 按强证据筛选 → 仍不唯一则 `AMBIGUOUS / ambiguous_match`；冲突无法消歧 → `role_conflict` | 场景 13 |
| 无法可靠判断时记录明确诊断 | `_element_digest()` + `format_role_diagnostics()` | 场景 11~15 |

## 七、线程边界与异常处理方式

### 7.1 线程模型

```
主线程（Qt GUI 线程）
  on_import_excel()
    ├─ QFileDialog.getOpenFileName(...)        ← 模态对话框，必须在主线程
    ├─ self._excel_importing = True            ← 防重复触发
    ├─ _set_excel_import_status("正在导入 Excel 文件...")
    └─ thread_pool.start(ImportExcelTask)      ← 立即返回（实测 0 ms）

工作线程（QThreadPool 线程）
  ImportExcelTask.run()
    └─ import_devices_from_excel(file_path, progress=...)
         ├─ parse_excel_devices()   读文件 + 流式解析 + 逐行校验（无 Qt）
         ├─ save_devices()           PBKDF2 并行加密 + 原子写盘（无 Qt）
         └─ progress(text) ─────────► _safe_emit(self, 'progress', text)

主线程（queued connection，自动回到 GUI 线程）
  _on_excel_import_progress(text)  → 更新 stat_label / progress_label / progress_bar
  _on_excel_import_finished(result) → 恢复进度条 → on_refresh() → InfoBar 报告结果
  _on_excel_import_failed(message) → 恢复进度条 → InfoBar 报告具体原因
```

### 7.2 线程边界的三条硬约束

1. **工作线程绝不触碰任何界面控件。**
   `appcore/excel_io.py` 模块**不 import 任何 Qt 模块**，是一个纯数据层；
   `ImportExcelTask.run()` 内部只有文件与字典操作。
2. **所有 UI 更新必须经信号槽回到主线程。**
   `ImportExcelSignals` 的三个信号由 `QRunnable` 线程发射，
   接收端是主线程的槽函数 → Qt 自动使用 queued connection。
3. **不做机械式整体搬迁。**
   `QFileDialog`（模态对话框）、`_set_excel_import_status`（进度条忙碌态）、
   `on_refresh()`（刷新设备列表）、`InfoBar`（结果弹窗）**全部留在主线程**；
   只有「读文件 → 解析 → 校验 → 加密 → 写盘」这段纯数据处理进了工作线程。

### 7.3 异常处理

| 场景 | 处理方式 |
|------|---------|
| 文件不存在 / 不是 xlsx / 表头缺列 / 无有效设备 | `appcore.excel_io.ExcelImportError`（携带具体中文原因）→ `ImportExcelTask` 捕获 → `error` 信号 → 主线程 InfoBar 显示原因 + 「原有设备配置未被修改。」 |
| 导入过程中发生未预期异常 | `log_exception(e, "Excel 导入")` 写入日志 + `error` 信号（不吞异常） |
| 窗口关闭时信号目标已销毁 | 复用项目已有的 `_safe_emit()`，把 `RuntimeError` / `AttributeError` 降级为日志，**不会让 PyQt6 因线程内未捕获异常 abort 进程** |
| 写入过程中失败 | `save_devices()` 原子写入：临时文件删除、**原 `devices.json` 保持不变**，不会留下半截 JSON |
| 导入中重复点击导入 | `_excel_importing` 标志位拦截，InfoBar 提示「已有一个 Excel 导入正在进行」 |
| 窗口关闭时正在导入 | `_shutdown_and_quit()` 额外 `thread_pool.waitForDone(30000)`，等写盘完成再退出 |
| 导入完成信号重复触发 | `finished` / `error` 两个槽都会把 `_excel_importing` 置回 `False` 并恢复进度条范围（幂等），`on_refresh()` 只在 `finished` 路径调用一次 |

class ImportExcelSignals(QObject):
    """Excel 导入信号"""
    progress = pyqtSignal(str)   # 阶段提示
    finished = pyqtSignal(dict)  # 导入结果
    error = pyqtSignal(str)      # 失败原因


class ImportExcelTask(QRunnable):
    """后台 Excel 导入任务。

    线程边界（重要）：
    - 工作线程只做**数据处理**：读文件、解析、校验、加密写盘；
    - **绝不创建、修改或删除任何界面控件**；
    - 界面更新（状态提示、列表刷新、结果弹窗）一律通过信号回到主线程；
    - 窗口关闭时信号发射异常由 _safe_emit 兜底，不会让进程 abort。
    """

    def __init__(self, file_path):
        super().__init__()
        self.file_path = file_path
        self.signals = ImportExcelSignals()

    def run(self):
        try:
            result = import_devices_from_excel(
                self.file_path,
                progress=lambda text: _safe_emit(self, 'progress', text))
            _safe_emit(self, 'finished', result)
        except Exception as e:
            log_exception(e, "Excel 导入")
            _safe_emit(self, 'error', str(e))

def encrypt_devices(devices, workers=None):
    """批量加密设备数据。

    每个字段使用**独立随机盐**加密，字段之间互不影响，因此可以安全地
    并行派生密钥：PBKDF2 在 OpenSSL 实现中会释放 GIL，多线程能真正并行。

    实测 100 台设备（200 个字段）串行约需 13 秒（PBKDF2 50000 轮，
    约 65ms/字段），这是 Excel 导入曾经把界面卡住十几秒的主因；
    并行后耗时大幅缩短，密文格式与串行完全一致（仍为 SALT: 前缀）。
    """
    if not devices:
        return []
    if workers is None:
        workers = min(len(devices), max(1, os.cpu_count() or 2))
    if workers <= 1:
        return [encrypt_device_data(d) for d in devices]
    with ThreadPoolExecutor(max_workers=workers) as pool:
        return list(pool.map(encrypt_device_data, devices))

def save_devices(devices):
    """加密并写入 devices.json（供 Excel 导入使用）

    采用「临时文件 + 原子替换」写入：加密或写盘中途失败时，
    原有的 devices.json 保持不变，不会留下被截断的半截文件
    （否则一次失败的导入会让设备配置直接损坏）。
    """
    from encrypt import encrypt_devices

    encrypted = encrypt_devices(devices)
    directory = os.path.dirname(CONFIG_FILE) or '.'
    os.makedirs(directory, exist_ok=True)
    fd, temp_path = tempfile.mkstemp(prefix='.devices_', suffix='.tmp',
                                     dir=directory)
    try:
        with os.fdopen(fd, 'w', encoding='utf-8') as f:
            json.dump(encrypted, f, ensure_ascii=False, indent=2)
            f.flush()
            os.fsync(f.fileno())
        os.replace(temp_path, CONFIG_FILE)
    except Exception:
        try:
            os.remove(temp_path)
        except OSError:
            pass
        raise
    Logger.info(f"已保存 {len(encrypted)} 台设备到 {CONFIG_FILE}")
    return encrypted
