# 验证码自动识别功能说明

> 适用版本：**6.0.1 起**（功能开关默认开启；6.0.2 起默认**区分大小写**；6.0.6 起支持无验证码页面跳过）
> 运行环境：**内网离线**，全部依赖为本地推理，不含任何联网调用。

---

## 1. 这个功能解决什么问题

登录页出现「数字 + 大小写字母」图片验证码时，历史版本的行为是：

> 检测到验证码输入框 → **不提交登录表单** → 停止并提示「需要验证码」 → 人工处理。

本功能在不改变上述**安全边界**的前提下，补齐了闭环：

```
定位验证码图片 → 截图 → OCR 识别 → 校验 → 填写 → 提交 → 判定结果
     ↑                                            ↓
     └────────── 刷新图片后重试（最多 4 次）←────┘
```

- 识别正确 → 自动填写并提交，登录成功；
- 服务端提示「验证码错误」 → 自动刷新图片并重试；
- 识别结果非法 / 置信度不足 → **不提交**，直接刷新重试；
- 服务端提示「密码错误 / 账号错误」 → **立即停止**（不重试，防止账号锁定）；
- 重试次数用尽 → 明确失败（`验证码自动识别失败（已尝试 N 次）`），不会无限循环。
  实际上限由**两个参数双重兜底**：`CAPTCHA_OCR_MAX_ATTEMPTS`（默认 30 次）与
  `CAPTCHA_ATTEMPT_BUDGET`（默认 60 秒），先到者为准。

## 2. 功能开关在哪里

| 开关 | 位置 | 说明 |
|------|------|------|
| 界面开关 | 主界面右侧「快捷登录」面板 →「自动识别验证码（数字+字母）」复选框 | 勾选 = 自动识别；取消 = 退回人工处理。**运行期即时生效，无需重启** |
| 代码开关 | `appcore/config.py` → `CAPTCHA_AUTO_ENABLED = True` | 界面开关的初始值 |

> **重要**：开关值必须通过 `appcore.config.CAPTCHA_AUTO_ENABLED` **模块属性**访问，
> 不要在其它模块里写 `from .config import CAPTCHA_AUTO_ENABLED`（那样会绑定旧值，
> 界面切换将不生效）。

### 关闭开关 / 未安装 ddddocr 时的行为

与历史版本**完全一致**：只定位并清空验证码输入框，**绝不提交登录表单**，
界面提示「需要验证码」。历史测试用例的断言保持不变。

## 3. 参数说明（appcore/config.py）

| 常量 | 默认值 | 含义 | 调参建议 |
|------|--------|------|----------|
| `CAPTCHA_AUTO_ENABLED` | `True` | 验证码自动识别总开关 | 不需要时置 `False` |
| `CAPTCHA_OCR_CHARSET` | 62 个数字+大小写字母 | 允许出现的字符集 | 必须与站点实际字符集一致 |
| `CAPTCHA_OCR_LENGTH` | `4` | 验证码长度（整条匹配，不裁剪） | 站点不是 4 位时改这里 |
| `CAPTCHA_OCR_CASE_SENSITIVE` | `True` | 是否区分大小写（**V6.0.2 起默认区分**） | 服务端**不**区分时置 `False` |
| `CAPTCHA_OCR_NORMALIZE_TO` | `"upper"` | 归一化方向（`upper`/`lower`） | 仅在 `CASE_SENSITIVE = False` 时生效 |
| `CAPTCHA_OCR_BETA` | `True` | 使用 ddddocr 的 `beta` 模型（精度更高） | 实测明显更差时可置 `False` 换标准模型 |
| `CAPTCHA_OCR_MIN_CONFIDENCE` | `0.5` | 置信度下限 | **最需要按实测调整**：误识别多 → 调高到 0.6~0.7；识别不出 → 调低到 0.3~0.4 |
| `CAPTCHA_OCR_PREPROCESS` | `True` | 灰度 + 对比度增强 + 2 倍放大 | 干扰强时保持开启 |
| `CAPTCHA_OCR_MULTI_PASS` | `True` | 多变体识别并合并结果 | 耗时敏感可关（只跑原始图） |
| `CAPTCHA_OCR_MAX_ATTEMPTS` | `30` | 最大尝试次数（含首次） | 实际还受 `CAPTCHA_ATTEMPT_BUDGET` 约束，一般不动 |
| `CAPTCHA_OCR_USE_OPENCV` | `False` | OpenCV 颜色过滤（去掉彩色干扰线） | ddddocr 会自带 `opencv-python`，开启此增强无需额外安装 |
| `CAPTCHA_IMAGE_LOOKUP_BUDGET` | `3.0` | 查找验证码图片的预算（秒） | 一般不动 |
| `CAPTCHA_REFRESH_WAIT` | `0.8` | 点击刷新后的等待（秒） | 图片刷新慢的站点调大到 1.2~1.5 |
| `CAPTCHA_RESULT_TIMEOUT` | `6` | 每次提交后的结果等待（秒） | 一般不动 |
| `CAPTCHA_ATTEMPT_BUDGET` | `60` | 带验证码重试的单次尝试总预算（秒） | **不要改回 20**：多次重试必然超时告警 |
| `CAPTCHA_SKIP_WHEN_TEMPLATE_EMPTY` | `True` | 模板声明无验证码时**跳过**查找（V6.0.6） | 一般不动 |
| `CAPTCHA_ABSENT_CACHE_ENABLED` | `True` | 记住「该模板 + 该页面确实没有验证码」（V6.0.6） | 一般不动；命中缓存后仍报验证码错误会自动清除并重查 |

## 4. 识别结果的校验规则

一条识别结果必须**同时满足**下列条件才允许提交：

1. `strip()` 后长度**恰好** `CAPTCHA_OCR_LENGTH`（4）；
2. 每一位都在字符集内（正则整条匹配 `^[0-9A-Za-z]{4}$`）；
3. 置信度 `>= CAPTCHA_OCR_MIN_CONFIDENCE`。

**任一不满足 → 整条作废**（返回空结果），**不允许删除非法字符后凑长度**。

大小写归一化**只在校验通过之后**做，绝不先转换再校验。
默认 `CAPTCHA_OCR_CASE_SENSITIVE = True`（**区分大小写**，V6.0.2 起），
此时字符集会同时接受大小写字母，且**不会**做任何大小写归一化。

## 5. 日志怎么看

正常识别：

```
[INFO] 验证码识别：'AB3D'（置信度=0.92，尝试 1/30）
[INFO] 验证码图片已定位（来源=语义规则，css=img[id*="captcha" i]）
```

识别失败并重试：

```
[INFO] 验证码识别结果无效（置信度=0.31，尝试 1/30），刷新后重试
[INFO] 服务端提示验证码错误，刷新后重试（尝试 1/30）
```

定位来源说明：

| 来源 | 含义 |
|------|------|
| `template` | 命中模板里的 `captcha_image_selectors`（第二次登录起优先） |
| `semantic` | 命中语义 CSS 规则（id/class/src 含 captcha/code/验证码 等） |
| `nearest` | 几何邻近兜底（验证码输入框 250px 内最近的图片） |

## 6. 模板新增字段

模板文件新增可选字段 `captcha_image_selectors`（验证码**图片**的定位规则）：

```json
{
  "name": "my-device",
  "username_selectors": [...],
  "password_selectors": [...],
  "login_button_selectors": [...],
  "captcha_selectors": [...],
  "captcha_image_selectors": [
    {"by": "CSS_SELECTOR", "value": "img[id*=\"captcha\" i]"}
  ]
}
```

- 历史模板**没有**该字段时静默补空列表，不产生任何告警；
- 模板录制会把实际生效的图片选择器写进去，保存模板后二次登录直接命中「模板」来源。

| 依赖 | 版本 | 作用 |
|------|------|------|
| `ddddocr` | 1.6.1 | OCR 引擎（内含本地模型） |

```bat
pip download ddddocr==1.6.1 onnxruntime==1.32.0 Pillow -d .\pkgs
```

**内网机器**离线安装：

```bat
pip install --no-index --find-links=.\pkgs ddddocr==1.6.1 onnxruntime==1.32.0 Pillow
```

打包（`build.bat`）已自动收集 ddddocr 模型与 onnxruntime DLL，
EXE 体积增加约 100~150MB，运行时**不需要 Python、不需要网络**。

## 8. 准确率实测与调参

### 8.1 实测方法

准备 100 张真实验证码截图（`01.png` … `100.png`）与对应真值
（`truth.txt`，每行一个 4 位验证码，顺序与文件名一致），然后执行：

```bat
python tools\measure_captcha_accuracy.py .\samples\captcha .\samples\truth.txt
```

输出示例：

```
样本数: 100
top-1 准确率: 87.00%  (87/100)
平均置信度: 0.91
低置信度(<0.50)被拒: 5
按字符准确率: 96.50%
```

### 8.2 当前实测状态（本机已实测）

在本机用**真实 ddddocr 引擎**（本地 ONNX 模型，离线）对模拟服务器生成的
100 张验证码（4 位数字+大小写字母、含 1~3 条干扰线与噪点、字符随机旋转）实测：

| 指标 | 实测值 |
|------|-------|
| 样本数 | 100 |
| **top-1 准确率** | **92.00%（92/100）** |
| 按字符准确率 | 97.00% |
| 平均置信度 | 0.975 |
| 置信度不足被拒 | 1 |
| 单张耗时 | 约 167ms（2 个变体：原图 + 预处理图） |

端到端验证（`tests/test_captcha_real_ocr.py`，**使用真实 OCR 引擎**、
不替换识别器）：3 轮登录**全部首次即识别成功**并跳转到 `/dashboard`。

> 结论：top-1 准确率 92% **远高于需求说明给出的 60% 上线门槛**，
> 可以按**默认参数**（置信度阈值 0.5、最多重试 4 次）直接上线。
>
> 上线后仍建议用本机真实站点的验证码样本再补测一次（步骤 8.1），
> 因为模拟样本的干扰强度与真实站点不一定相同。

### 8.3 上线判据与调参建议

| 实测 top-1 准确率 | 结论与动作 |
|------------------|-----------|
| `>= 85%` | 可直接上线，保持默认参数（阈值 0.5、4 次重试） |
| `60% ~ 85%` | 可上线但需调参：把 `CAPTCHA_OCR_MIN_CONFIDENCE` 提到 **0.7**，把 `CAPTCHA_OCR_MAX_ATTEMPTS` 提到 6；同时开启 `CAPTCHA_OCR_USE_OPENCV`（干扰线为固定颜色时） |
| `< 60%` | **不得直接上线**。按需求说明第 5 节，需提出自训小模型方案（用同样的 100+ 样本微调一个 4 字符分类/识别模型），或改用「识别 + 人工确认」半自动模式 |

其它调参提示：

- 误识别多（提交后总是「验证码错误」）→ 提高 `CAPTCHA_OCR_MIN_CONFIDENCE`；
- 一直识别不出（结果非法）→ 降低阈值到 0.3，并确认 `CAPTCHA_OCR_LENGTH` 与字符集是否匹配站点；
- 站点图片刷新慢 → 提高 `CAPTCHA_REFRESH_WAIT`；
- 批量登录整体变慢 → 关闭 `CAPTCHA_OCR_MULTI_PASS`（只跑原始图，少一次预处理推理）。

## 8.4 真实站点实测（区分大小写站点）

在 `http://test.my.cn/captcha_login.php`（4 位、**区分大小写**、彩色干扰线 +
噪点、小字号衬线字体）上做了真实浏览器 + 真实 ddddocr 的端到端实测，
结论如下。

### 结论一：元素截图会把 CSS 边框一起截进来，必须取原始像素

该站点的验证码图片带 `border:1px solid #dcdfe6`：

| 取图方式 | 图片尺寸 | ddddocr 结果 |
|----------|----------|--------------|
| `element.screenshot()`（元素截图） | 150 x **49**（含灰边） | **空串**（完全识别不出） |
| 原始图片像素（canvas 导出） | 150 x 48 | 能正常输出 4 位 |

**已修复**：`browser.capture_captcha_image()` 改为用 canvas 导出 `<img>` 的
原始像素（不含边框、不受 CSS 缩放影响、也不会重新请求图片换掉验证码），
失败时再退回元素截图。

### 结论二：失败一次后验证码立即作废，无法"同图换大小写重试"

实测流程：先提交错误验证码 → 再用同一张图上的**正确答案**提交 → 仍然失败。
原因是服务端在失败后重新渲染页面并刷新图片，验证码已换新。

因此大小写变体只能靠"下一次刷新后的新图"重新识别，**不能**在同一张图上依次尝试。

### 结论三：逐次独立成功率约 15%~20%

每轮使用全新会话、单次提交（模拟程序的一次尝试）：

| 识别配置 | 每轮 4 次尝试的成功率 |
|----------|----------------------|
| beta 模型、**不**做颜色过滤 | **约 17%** |
| beta 模型 + ddddocr 颜色过滤 | 0%（过滤把字符抗锯齿边缘一起抹掉，笔画变细反而更难识别） |
| 标准模型 + 灰度放大 | 0%~17% |

**已据此调优**：

- `CAPTCHA_OCR_COLOR_FILTER = False`（默认关闭颜色过滤）；
- 每次尝试都使用**最优变体**（不再轮换到较弱变体，避免浪费尝试机会）；
- `CAPTCHA_OCR_MAX_ATTEMPTS = 6`（4 次约 50%~60%，6 次约 65%~75%）。

### 结论四：主要误差是"大小写"，字符本身通常是对的

抽查失败样本（人工核对）：

| 真实值 | OCR 结果 | 问题 |
|--------|----------|------|
| `sKu4` | `sku4` | `K` 判成 `k` |
| `7dZv` | `7dzv` | `Z` 判成 `z` |
| `5o5M` | `565m` | `o` 判成 `6`，`M` 判成 `m` |

即：**区分大小写的站点上，ddddocr 的大小写判别准确率是本功能的瓶颈**。

### 结论五：加「去彩色干扰」掩膜后成功率提升约 3 倍

真实站点上按「只保留暗且低饱和（黑色字符）像素」做掩膜、再放大 3 倍，
单次识别成功率从约 3%~7% 提升到约 **15%**，对简单验证码仍为 100%：

| 预处理 | 4 位合法输出 | 单次成功率 |
|--------|-------------|-----------|
| 原始图 | 约 20%~35% | 约 3%~7% |
| 灰度 + 对比度 + 3 倍放大 | 约 80% | 约 7%~15% |
| **颜色掩膜（S<70,V<175）+ 3 倍放大** | **约 80%** | **约 15%** |

已把颜色掩膜作为**首选变体**（`CaptchaRecognizer._variants_spec()`），
同一张图会依次尝试多个掩膜/灰度变体并取最可信的合法结果。
重试次数相应调整到 `CAPTCHA_OCR_MAX_ATTEMPTS = 10`。

### 结论七：靠「多次独立重试」累积成功率

已验证：提交错误后验证码**立即作废**（用同一张图穷举 16 种大小写组合，
无一命中），所以「同图换大小写重试」不可行，每次尝试都是一次全新机会。

因此把重试改成**时间预算驱动**：

- `CAPTCHA_ATTEMPT_BUDGET = 60`：单次尝试（含刷新 + 识别 + 提交 + 判定）
  约 2~3 秒，60 秒内可试 20~30 次；
- `CAPTCHA_OCR_MAX_ATTEMPTS = 30`：次数上限。

按单次 15% 估算：10 次约 80%、20 次约 96%、30 次约 99%。

**端到端实测**（真实入口 `login_device`，每轮全新浏览器会话）：
6 轮全部登录成功，单轮 6.5~21.7 秒；失败的轮次会明确提示
「验证码自动识别失败（已尝试 N 次）」，不再误报「已完成」。

### 结论九：多预处理变体要用「多数票」，不能只看置信度

实测（区分大小写站点，字符真值 `TzK2`）：

| 变体 | 结果 | 置信度 | 对错 |
|------|------|--------|------|
| 原始图 | `tzk2` | 0.98 | **错**（`K` 认成 `k`） |
| 灰度 3 倍 | `TzK2` | 0.97 | 对 |
| 颜色掩膜 3 倍 | `TzK2` | 0.99 | 对 |

按「最高置信度」会选到**错的**原始图结果；按**多数票**（2:1）才能选到对的。
因此 `CaptchaRecognizer` 的多变体合并已改为多数票，置信度仅作平票时的兜底。

### 结论十：不同站点的登录按钮写法差异很大

| 站点 | 登录按钮 | 说明 |
|------|----------|------|
| test.my.cn | `<button type="submit">登 录</button>` | 标准表单提交 |
| mingshi8.hbte.com.cn | `<button type="submit" class="btn-submit">提交</button>` | 按钮文字是「提交」 |
| 210.12.41.116:8989 (H3C) | `<a id="myButton" class="submit">立刻登录</a>` | **不是 button，是 `<a>`** |

H3C 这类设备管理页如果用泛化规则 `ID=login`，会命中页面上**不可见**的
`id="login"` 容器，点了没反应，表现为「登录结果未确认」。
因此 `<a>` / `<div>` 形式的按钮规则必须排在泛化 ID 规则**之前**。

### 结论十一：验证码输入框「获得焦点即刷新」的站点

部分设备管理页（H3C WebUI 等）在**验证码输入框获得焦点时就会刷新验证码**：

| 操作 | 验证码图片 |
|------|-----------|
| 初始 | 图 A |
| **点击输入框** | **图 B（变了）** |
| 之后再输入字符 | 不变 |

如果按「先截图识别 → 再填输入框」的顺序，填输入框这一步会触发刷新，
等于**提交刷新前的旧码**，必然失败。

处理方式（两道保险）：

1. 每次尝试**先激活（点击）验证码输入框**并等图片加载完，再截图识别；
2. 填写前后**比对图片指纹**（canvas 原始像素 MD5），
   发现被刷新就**自动重新识别并重新填写**。

### 结论十二：登录提交「回车优先」

绝大多数站点（实测约 90%）在输入框按回车即可登录，而登录按钮有时是
`<a>` 或受 JS 事件约束，点击未必生效。

现在的提交策略：**回车优先 → 无反应则回退点击按钮**。
判断「回车有没有反应」用一次 1.5 秒的短等待（是否出现错误提示 / URL 变化 /
成功特征），避免每次尝试都白等 6 秒。

### 结论十七：无验证码页面不必每次都查找

设备模板的 `captcha_selectors` / `captcha_image_selectors` 都是空列表，
说明该页面本来没有验证码。此时**直接跳过验证码查找**（0ms），
不再把「模板候选 + 内置候选」几十个选择器空跑一遍。

同时会把「该模板 + 该页面无验证码」的结论持久化到
`APP_DIR/captcha_absent.json`，下次登录直接跳过。

| 场景 | 验证码查找耗时 |
|------|----------------|
| 模板声明无验证码 | **0ms** |
| 陈旧模板首次查找 | 约 450ms（并写入缓存） |
| 同一模板/页面第二次登录 | **0ms** |

**安全兜底**：若跳过之后服务端仍提示「验证码错误」，会自动清除缓存并
重新完整查找一次，因此页面后来新增了验证码也不会被缓存卡死。

可用开关关闭该优化：
`CAPTCHA_SKIP_WHEN_TEMPLATE_EMPTY` / `CAPTCHA_ABSENT_CACHE_ENABLED`（均在 `config.py`）。

### 结论十五：验证码错误后的表单状态不可假设

不同站点在「验证码错误」后的行为完全不同：

| 站点行为 | 处理方式 |
|----------|----------|
| 清空账号密码（整表重置） | 每次提交前**重填账号密码并校验**；失败则重新定位字段再填 |
| 什么都不清空（错误码留在框里） | 每次重试前先清空验证码框；最终失败退出前也清空 |
| 点击验证码框就重置表单 | 先激活输入框触发刷新，再重填账号密码 |

实现要点：`_ensure_credentials_filled()` 不会「填完就算」——
它会检查是否真的写进去了；写不进去就重新定位字段重试，
仍然失败则明确报「账号/密码无法填写」，**绝不拿空账号去提交**
（否则会被服务端判成密码错误并停止重试）。

### 结论十六：表单定位不到时先看「表单诊断」日志

登录失败时日志会输出一行诊断，例如：

```
表单诊断：inputs=2 frames=0 title=用户登录 url=http://... 
         [type=text name=username vis=1] [type=password name=password vis=1]
```

可以据此判断：页面上有没有输入框、是否 `vis=0`（不可见）、
`frames` 是否大于 0（表单在 iframe 里）、`name/type/placeholder` 是否符合预期。

另外定位失败会自动「等 2 秒再完整重试一次」，覆盖 SPA 首屏后才渲染表单的情况。

### 结论十四：验证码可能是内联 SVG，不一定是 <img>

有些登录页（el-input / Vue 风格）把验证码画成**内联 SVG**：

```html
<div class="code-content">
  <svg width="150" height="50" viewBox="0 0 150 50">
    <rect width="100%" height="100%" fill="#ABCC..." />
    <path fill="#73635a" d="M20.82 49.53..." />
  </svg>
</div>
```

只找 `img` / `canvas` 会直接报「找不到验证码」。

现在支持：

| 环节 | 做法 |
|------|------|
| 定位 | 语义规则 `svg[class*="code"]`、`[class*="code-content"] svg`、`svg[class*="captcha"]` 等；几何兜底也纳入 `svg` |
| 取图 | 序列化 SVG → data URL → `Image` → `canvas` → PNG（`drawImage` 不能直接吃 `<svg>` 元素） |
| 深色主题 | 图片整体偏暗（>55% 像素亮度 < 100）时自动反色成「浅底深字」 |

### 结论十三：换电脑报「找不到指定的模块」= 包内缺运行库

同一份 EXE 在不同电脑上表现不同，多数是**包内缺 DLL**：

| 缺失项 | 原因 | 表现 |
|--------|------|------|
| `icu.dll` | Windows 上的 `icuuc.dll` 只是 36KB 转发 DLL，实现/数据在 `icu.dll`；Win10 1903 以下没有 | `QtGui: 找不到指定的模块` |
| `msvcp140_2.dll` 等 VC++ 运行库 | PyInstaller 只收集检测到的几个；构建机装了运行库，目标机没装 | 同上 |

**修复**：`appcore/packaging_utils.py` 显式收集 PyQt6 自带的整套 VC++ 运行库
（`msvcp140*` / `vcruntime140*` / `concrt140` / `vccorlib140`）以及系统
`icu.dll` / `icuin.dll`，由 `create_spec.py` 打进包（同时放根目录与
`PyQt6\Qt6\bin\`）。打包后不再依赖目标机环境。

> 自检方法：用 `pyi-archive_viewer` 或构建 TOC 确认包里含
> `icu.dll`、`msvcp140_2.dll`、`msvcp140_atomic_wait.dll`。

### 结论八：试过但**没有**用的办法（避免重复踩坑）

| 尝试 | 结果 |
|------|------|
| ddddocr 内置颜色过滤 `color_filter_colors` | **0%**，会把字符抗锯齿边缘一起抹掉 |
| ddddocr `std` / `old` 模型 | 比 `beta` 差（4 位输出率 1/16 ~ 2/16） |
| RapidOCR（PP-OCR）检测+识别 / 仅识别 | 5%~10%，且慢 10 倍 |
| 形态学连通域切分字符 | 字符只有 1~2 像素宽，连通域被线条粘连，不可靠 |
| 均分 4 段后逐字识别 | 15%，与整图识别持平 |
| 放大倍数 3~12 扫描 | 15% 左右封顶，不再提升 |
| 同一张图穷举大小写组合 | **不可行**：错一次验证码即作废 |
| 服务端是否泄漏验证码 | 未发现（HTML / 响应头 / Cookie 均无） |

结论：**该验证码（150×48、衬线小字、约 8 条彩色干扰线交叉、彩色噪点）
已超出通用 OCR 的可靠识别范围**。要再往上提，只能用该站真实样本
（≥500 张）自训专用模型。

### 结论六：登录成功判定与「已登录」判定

该站点登录成功后 **URL 不变**（`captcha_login.php`），只是页面内容变成
「登录成功 / 欢迎，admin！/ 退出登录」。因此新增两层判定：

- `SUCCESS_KEYWORDS`：页面出现「欢迎 / 登录成功 / 退出登录 / 注销」等即判定成功；
- 已登录检测：先看成功特征，再看 URL —— 之前因为 URL 里含 `login`
  而把「已登录」误判成「找不到登录表单」。

另外补充了常见站点的选择器（如 `input[name="user_code"]`、`确认登录` 按钮等），
以适配不同站点的验证码输入框与登录按钮写法。

### 上线建议（区分大小写站点）

- 若站点**区分大小写**：保持 `CAPTCHA_OCR_CASE_SENSITIVE = True`（默认），
  接受约 15%~20% 的单次成功率；6 次重试后仍失败时退回人工处理；
- 若需要稳定高成功率（≥ 80%）：按需求说明第 5 节，用该站点的真实样本
  （≥ 500 张）**自训 4 字符识别模型**，替换 `CaptchaRecognizer` 的引擎实现；
- 若站点**不区分大小写**：把 `CAPTCHA_OCR_CASE_SENSITIVE` 置 `False`，
  单次成功率会显著高于上述数字。

---

## 9. 已知边界

- 通用元素发现路径（`_run_generic_attempt`）**不**自动处理验证码，
  需要验证码自动识别的页面请使用模板路径；
- 不区分大小写的前提来自需求确认；服务端若区分大小写，需把
  `CAPTCHA_OCR_CASE_SENSITIVE` 置 `True`；
- 不支持「算术题」「拼图」类验证码，只支持字符型图片验证码。
