## 0. 先说明：任务书描述与真实代码的差异

任务书基于 **V5.0.6** 的运行日志提出问题。本次审查的代码库已是 **V5.0.10**，两者的**行为描述与日志字段名不一致**，直接照抄需求会改错地方。以下差异已逐条核实：

| 维度 | 任务书日志样例（V5.0.6） | 当前代码库（V5.0.10） | 核实方式 |
|---|---|---|---|
| 查找阶段名 | `submit lookup` | `username_lookup` / `password_lookup` / `captcha_lookup` / `login_button` / `template_*` | 代码走查 `appcore/login_engine.py`、`appcore/browser.py` |
| 汇总字段名 | 候选总数 / 实际开始执行 / 执行完成 / 因预算不足未执行 / 不完整查找 | `total` / `unique_total` / `executed` / `completed` / `hits` / `skipped` / `not_executed` / `not_executed_error` / `duplicates` / `role_rejected` / `exit_reason` / `incomplete`，汇总行标题 `[选择器查找汇总]` | `appcore/browser.py` 查找引擎返回结构 + `tests/test_lookup_stats.py` 断言 |
| 默认模板规模 | 日志显示「35 个用户名选择器」 | 磁盘 `templates/default.json` 实测 `username_selectors = 35` 条、`password_selectors = 21`、`login_button_selectors = 17`、`captcha_selectors = 14` —— **与任务书完全吻合** | 实测脚本读取 `templates/default.json` |

**结论**：任务书的规模描述与当前代码库真实状态一致，可以直接作为验证基准；仅日志字段名需按 V5.0.10 现状对齐。任务书第 6 项「密码查找与登录按钮查找用了相同的 `input[type="password"]`」经实测**在当前代码库中不成立**（详见 D-06）。

## 1. 已确认问题清单（逐条根因与证据）

> 收录标准：有**代码证据**或**可复现的测试证据**支持的问题。推测性内容一律归入第 2 节「待验证风险」。

### D-01 改 devices.json / 模板后点「刷新配置」没有真正重载

- **根因**：原「刷新」实现只重新读取设备列表并刷新界面控件，**没有让模板管理器丢弃内存缓存**。`TemplateManager` 内部维护 `_templates` / `_sources` / `_errors` / `_loaded` / `_lock`，缓存命中时直接返回旧对象，磁盘上的新文件根本没被读；登录任务又通过 `_resolve_template()` 按模板名实时取模板，因此继续使用内存中的旧模板。
- **证据**：
  - `appui/main_window.py::on_refresh` 现状为「快照 → `reload_templates(force=True)` → `load_devices` → 校验 → 成功才切换 / 失败回滚」。
  - `appcore/templates.py` 新增 `reload_templates(force=...)` 与 `restore_templates(snapshot)`。
  - `appcore/login_engine.py::_resolve_template`（约 263–319 行）按登录尝试**实时解析**模板，刷新后对新任务立即生效。
  - 回归：`tests/test_config_refresh.py`（58 项）覆盖「改磁盘文件 → 刷新 → 内存/UI/后续任务同步」与「配置非法 → 保留最后有效配置」。
- **修复后行为**：刷新会真正重读磁盘、重建模板缓存与设备列表、分组 UI 同步重建；解析校验失败时**不先清空**，保留最后一次有效配置并提示具体文件与原因，允许改好后再次刷新。

### D-02 默认模板被内置版本覆盖、缺少可靠的追加方式

- **根因**：内置模板（`PRESET_TEMPLATES`）与用户磁盘模板没有清晰边界；启动/刷新/保存时无条件用内置版本重写磁盘 `templates/*.json`，用户手工加的选择器被抹掉；同时「追加新选择器」只能靠手工编辑 JSON，没有受控入口。
- **证据**：
  - `appcore/templates.py::create_default_template_files` 现状规则：**文件不存在 → 写入内置完整版本（唯一一次「内置覆盖磁盘」）；文件已存在 → 不整体覆盖，只补齐缺失/为空的字段；与内置完全一致 → 不写盘**。
  - 新增受控 API：`append_selectors_to_default` / `merge_template_into_default` / `replace_default_template`；`replace_default_template` 强制 `strict_roles=True`（角色冲突直接拒绝写入）。
  - UI 最小改造：`appui/main_window.py` 的「工具」菜单新增「默认模板」子菜单（追加 / 合并 / 替换三个 QAction）。
  - 回归：`tests/test_config_refresh.py::run_preset_template_scenarios`（5 项）与 `run_role_mapping_scenarios`（18 项）。

### D-03 模板有 35 个用户名选择器，最终统计却显示「实际开始执行 = 1」

- **根因**：旧统计把**去重前的原始候选**当作总数，把「命中后提前退出」后**实际执行过的候选**当作「实际开始执行」，两个口径混用，导致「候选总数 = 35」与「实际开始执行 = 1」并存且互相矛盾（命中即退出时，执行数天然为 1，看起来像"只跑了第一个"）。
- **证据**：`appcore/browser.py` 查找引擎现在**分字段**返回 `total / unique_total / executed / completed / hits / skipped / not_executed / not_executed_error / duplicates / role_rejected / exit_reason / incomplete`，`incomplete` 按实际执行情况计算；`tests/test_lookup_stats.py`（95 项）逐字段断言，其中：
  - 「3 去重后候选数 = 30」→ 证明去重前后口径分离；
  - 「2 因命中提前退出未执行 = 0」「2 退出原因不是 hit」「2 不完整查找 = 否（全部候选都执行过）」→ 证明未命中场景下全部候选都真实执行过；
  - 「6 退出原因 = budget_exceeded」「6 因预算不足未执行 > 0」「6 不完整查找 = 是」→ 证明预算不足场景如实记账；
  - 「4 密码与按钮命中的是不同候选」→ 见 D-06。
- **修复后行为**：日志中「原始候选总数 / 去重后候选数 / 实际执行数 / 执行完成数 / 命中数 / 因命中提前退出未执行数 / 因预算不足未执行数 / 因异常未执行数 / 最终退出原因」分项独立输出，`不完整查找` 与实际执行一致；**没有删除任何诊断字段**。

### D-04 用户名选择器命中后填写失败（任务书问题 ⑦）

- **根因（经核实为「非缺陷」）**：任务书怀疑「命中用户名后填写失败仍继续提交」。实际代码路径 `appcore/login_engine.py::_locate_and_fill`（约 542–637 行）在用户名或密码任一填写失败时**立即 `return`**，`_run_template_attempt`（约 683–687 行）直接返回失败结果，**不会错误地继续走提交流程**。
- **证据**：代码走查 + `tests/test_real_login.py`（42 项，真实 Playwright 驱动本地测试页）覆盖「密码错误 → 不提交成功路径」。
- **结论**：**不是缺陷**。真正会命中的相邻缺陷是 D-09（元素引用失效被误报为不可见）与 D-10（多匹配消歧失效）。

### D-05 默认模板中 `input[name="login"]` / `input[id="login"]` 可疑（任务书问题 ⑤）

- **根因**：旧流程只按「选择器写法像不像用户名」判断，**从不检查目标元素的真实角色**，`name="login"` 这类只表明字段用途、不表明控件类型的属性会被当成用户名输入框。
- **证据**：`appcore/element_roles.py`（新增，21.4 KB）实现角色校验：
  - **结构性强校验**：标签类型、`type`、可见性、可用/可编辑状态、隐藏、只读；
  - **语义弱校验**：否定式否决（按钮 / 提交控件 / 密码框 / 验证码框 / 隐藏字段 → 否决）+ 多匹配歧义消解；
  - 离线静态规则 `static_role_risk(field_key, selector)`：**不依赖页面**即可判定「选择器写法与目标字段角色冲突」。
  - `tests/test_element_roles.py`（35 项）覆盖 9 类本地页面场景。
- **实测**：对内置 `DEFAULT_TEMPLATE` 与磁盘 3 个模板逐条跑 `static_role_risk`，**命中数均为 0** → 说明现有默认模板没有角色冲突，接入校验不会产生误报警告。

### D-06 密码查找与登录按钮查找用了相同的 `input[type="password"]`（任务书问题 ⑥）

- **根因（经核实：当前代码库不存在该映射错误）**：实测磁盘 `templates/default.json`：
  - `password_selectors`（21 条）∩ `login_button_selectors`（17 条）= **∅**
  - `username_selectors`（35 条）∩ `password_selectors` = **∅**
  - `username_selectors` ∩ `login_button_selectors` = **∅**
  - 代码侧 `appcore/login_engine.py::_submit_login` 独立取 `template.get('login_button_selectors', [])`，**不使用密码列表**；`appcore/browser.py::find_login_button_by_selectors_detailed` 独立调用 `_lookup_selectors(role=ROLE_BUTTON)`。
- **V5.0.6 日志中「submit lookup 用 `input[type=password]`」的最可能来源**：`appcore/browser.py::click_login_button_detailed`（约 1952–2050 行）的**回车提交兜底**——当模板按钮与通用按钮选择器都没命中时，会在密码框上按回车提交（当前版本已显式标注 `source='enter'`，并在日志中与真实点击区分）。
- **结论**：**不是字段映射缺陷**，而是「回车提交兜底」在旧版日志中未标注来源造成的观感误解。已在 D-05 的角色校验下进一步收敛。

### D-07 启动后主界面已显示但数据加载慢（任务书问题 ①）

- **根因**：设备加载阶段对 **每台设备的每个加密字段**做一次 PBKDF2-HMAC-SHA256 密钥派生（50000 轮，实测约 60ms/字段），3 台设备即约 380ms，界面长时间停留在「正在加载设备数据…」。
- **证据**：`appcore/devices.py` 现为**按需解密**——`load_devices()`（52–81 行）只解析文件并分组（毫秒级），`get_device_credentials()`（84–118 行）在真正登录某台设备时才解密该设备的两个字段，并把明文回写缓存，同一台设备不重复解密；**文件解析失败仍然抛异常，不会静默丢设备**（未降低校验标准）。
- **配套**：`appcore/tasks.py` 把设备加载放到 `LoadDevicesTask`（QRunnable）后台线程；`main.py` 增加分阶段 `[启动耗时]` 计时日志。
- **数据**：见第 8 节。

### D-08 `input_text_detailed` 把「元素引用失效」误报为「不可见」

- **根因**：Playwright 的 ElementHandle 在 DOM 重渲染后会 detached，此时 `is_visible()` 抛异常，旧代码把异常兜底成「不可见」，导致真正的失败原因（元素已失效）被掩盖，后续重试策略也用错。
- **证据**：`appcore/browser.py` 新增 `_is_detached` 判定，`input_text_detailed` 增加 `element_detached` 归类；`tests/test_lookup_stats.py`、`tests/test_real_login.py` 覆盖。

### D-09 `quick_check_locator` 返回 `.first` 使多匹配消歧失效

- **根因**：快速存在性检查直接返回 `.first`，即使页面上有多个匹配元素也会取第一个去填写，**违背「不允许把未经验证的元素当成正确的登录元素」**。
- **证据**：`appcore/browser.py::quick_check_locator` 改为返回完整 locator，使多匹配能被上层识别为歧义；`tests/test_element_roles.py` 场景 5：「5 多匹配被识别为歧义」「5 歧义时不给出发写元素」「5 多匹配时不会直接取第一个填写」。

### D-10 `get_attribute('readonly')` 真值判断使只读元素挂起 30 秒

- **根因**：HTML 布尔属性 `readonly` 存在时 `get_attribute('readonly')` 返回**空字符串**，`if value:` 判为 False → 只读输入框被当作可填写元素，Playwright `fill()` 一直等到超时（30s）。
- **证据**：`appcore/browser.py` 改用 `is not None` 判断；新增 `_fill_with_timeout` 限制单次填写等待；`tests/test_element_roles.py` 场景 6：「6 同名的隐藏/禁用/只读元素整体不可用」「6 可见用户名框不受影响」。

### D-11 模板保存 / 加载路径缺少「字段 ↔ 元素角色」映射校验（任务书 2.3 / 6.2 / 7.1）

- **根因**：`appcore/templates.py` 的 `validate_template` 只校验 JSON 语法与字段结构，**不校验选择器与字段角色是否冲突**；因此一个「把 `input[type=password]` 写进 `username_selectors`」的模板可以被正常保存并直接用于登录。
- **证据**：
  - 新增 `appcore/templates.py::_collect_role_risks()` 收集角色冲突；
  - `validate_template(data, source='', check_roles=True)` 在空字段警告之后追加角色警告（**只警告不阻断加载**，不影响既有模板可用性）；
  - `write_default_template(data, strict_roles=False)`：`strict_roles=True` 时角色冲突**直接拒绝写入并指出具体字段与选择器**；`replace_default_template` 使用 `strict_roles=True`；
  - `tests/test_config_refresh.py::run_role_mapping_scenarios`（18 项）覆盖 9 类角色冲突。
- **实测安全性**：`static_role_risk` 对内置模板与磁盘 3 个模板命中数均为 0。

### D-12 内置预置模板与磁盘模板字段不同步 + `_repair_preset_template` 补齐逻辑错误

- **根因（打包态实测发现）**：内置 `PRESET_TEMPLATES` 的 `proxmox` / `huawei` **缺少 `captcha_selectors` 字段**；而 `_repair_preset_template` 把「内置版本里本来就不存在的字段」也当成「用户文件缺失字段」去补一个空列表 → **每次用户首次升级该版本时都会改写自己的预置模板文件**，并打出「预置模板不完整，已补齐缺失字段: proxmox.json / huawei.json」的误报警告。
- **证据**：
  - 修复：内置 `proxmox` / `huawei` 补 `'captcha_selectors': []`；`_repair_preset_template` 跳过 preset 中不存在的字段（注释：「内置版本本身就没有的字段，不属于『缺失字段』，不得凭空补一个空列表」）。
  - 实测：内置与磁盘 `_same_template_content` 全为 True；连续两次 `create_default_template_files` **不写盘**；老文件只补一次。
  - 打包态离线验证：重启日志中**不再出现**该告警。
  - 回归：`tests/test_config_refresh.py::run_preset_template_scenarios`（5 项）。

### D-13 `bump_version.py` 往返不幂等（修订号被抹除、递增规则注释乱序）

- **根因**：`_tuple_text()` 恒写 `, 0`，`APP_VERSION_INFO` 第 4 位修订号在升/降版往返后丢失；`update_config` 的「递增规则」注释按 `(old, new, next(new))` 生成，**降版时会写出乱序链**（如 `5.0.11 -> 5.0.10 -> 5.0.11`），导致「升版 → 降版」无法逐字还原 `appcore/config.py`。
- **证据**：`bump_version.py` 新增 `_current_revision()`（读取并保留修订号）、`_tuple_text(version, revision=None)`；`update_config` 注释改为**以新版本为链头**（幂等，与升降版方向无关）。
- **回归**：`tests/test_bump_version.py`（59 项）。

### D-14 版本号测试在真实项目目录做往返，污染用户文件

- **根因**：`tests/test_bump_version.py` 的往返测试直接在**项目根目录**执行升版/降版，实际改写了用户的 `README.md` / `技术文档.md` / `CHANGELOG.md` / `appcore/config.py` —— 违反任务书 8.3「避免污染真实用户数据」。
- **证据**：往返测试改为在 `tempfile.mkdtemp()` 的**临时工作副本**中执行（`make_workspace()` / `run_bump_in()` / `version_of()` / `state_of()`），并新增断言「测试未污染真实项目文件」；实测测试前后项目文件哈希一致。

### D-15 `AutomationLoop.shutdown()` 丢弃未退出 daemon 线程的引用

- **根因**：`join(timeout=10)` 超时后仍无条件执行 `self._thread = None`，**丢掉对仍在运行的 daemon 线程的引用**。解释器退出时该线程被强制终止，若此刻正停在 asyncio / Playwright 的 C 扩展内部，会造成 `0xC0000005`（访问冲突）闪退。
- **证据**：`appcore/automation.py::shutdown` 现状为「join 超时 → 记录 WARNING → **保留线程引用并 return**」，既不谎报「已停止」，也避免退出期强杀；新增 `tests/test_exit_safety.py`（13 项）做回归防护。

### D-16 `QRunnable` 线程中的未捕获异常会让 PyQt6 直接 abort 整个进程

- **根因**：后台任务线程里访问已被销毁的信号对象会抛 `RuntimeError`；而 QRunnable 线程中未捕获的 Python 异常会让 PyQt6 直接 abort 进程（表现为闪退，且不给出可读堆栈）。
- **证据**：`appcore/tasks.py` 新增 `_safe_emit()` / `_safe_call()`，把「取信号对象」与「发射信号」都放进 try 兜底并写入日志；**真实业务异常仍由各自的 except 分支处理并上报，不会被吞掉**，只把「目标对象已销毁」这一类关闭时序异常降级为日志。

### D-17 模板「追加 / 合并 / 主动替换」三种语义未区分，整体替换无用户确认

- **根因**：旧实现只有「整体写入」，无法表达「只加新的、不动原有的」，也没有把「整体替换」与「追加」区分开，整体替换缺少明确确认环节。
- **证据**：`appcore/templates.py` 提供三个语义明确的 API（追加 / 合并 / 替换），替换走 `strict_roles=True` 角色校验；`appui/main_window.py`「工具 → 默认模板」菜单提供三个入口；「保存失败不破坏原文件」由**原子写入**（`tempfile.mkstemp` + `os.replace`）保证；`tests/test_config_refresh.py` 覆盖「追加不被模板原有内容中的角色冲突选择器阻塞」「整体替换拒绝角色冲突的选择器」「拒绝时默认模板文件未被破坏」「用内置版本整体替换默认模板成功」。

## 2. 待验证风险清单（含尚未确认的原因）

> 以下条目**没有**取得可复现证据，或证据不足以判定为缺陷，按任务书要求标注为「待验证风险」，不写成确定根因。

### R-01 退出期偶发 `0xC0000005`（Windows 访问冲突）

- **观测事实**：全量回归中 `tests/test_ui_theme.py` 曾出现一次进程退出码 `3221225477`（`0xC0000005`），但**该文件 34 项断言全部 PASS**；`tests/test_report.txt` 中该次 stdout **缺少 `report()` 的汇总行** → 崩溃发生在 Python 解释器退出阶段（stdout 块缓冲未刷新）。
- **复现尝试与结果**：
  - 单跑 10 次 + 压测 60 次（`_rc_probe.py`，与 `run_all.py` 相同的 `capture_output` 方式）→ **全部 rc=0**；
  - 裁剪式复现脚本 3 组模式（只建 QApplication / 建窗口不退出 / 完整退出路径）各 12 次 → **全部 rc=0**；
  - 累计 **106 次未复现**。
- **尚未确认的原因**：无 Python 堆栈（崩溃在 C++ 层），无法定位到具体对象析构顺序；候选假设包括 Qt offscreen 插件退出期行为、QApplication 与 QWidget 的析构顺序、InfoBar/MessageBox 的 `deleteLater` 队列 —— **均为推测，未验证**。
- **已做的加固（降低概率，非消除根因）**：
  - `appcore/automation.py`：见 D-15，消除「daemon 线程被无保护强杀」这一**有代码证据**的成因；
  - `tests/test_ui_theme.py` / `tests/test_gui.py`：退出后显式 `window.deleteLater()` + `app.processEvents()`，让 Qt 在解释器退出前完成正常销毁顺序。
- **状态**：**待验证风险**，未列入已确认缺陷。

### R-02 多实例并行运行会争抢 `app.log` 与 `templates/`

- **观测事实**：离线验证时用 `Stop-Process` 结束 onefile bootloader，**子进程仍存活**并继续持有 `app.log`；多个实例同时存在时日志归属与文件占用关系不确定。
- **尚未确认的原因**：项目当前**没有单实例保护**（未找到互斥锁 / 命名互斥体），无法判断这是否会在真实使用中造成模板文件写入冲突。
- **状态**：**待验证风险**，属既有设计，未在本次任务范围内改动。

### R-03 打包产物在 `%TEMP%` 留下 `_MEI*` 解压目录（运维风险）

- **观测事实**：本次验证期间实测 C 盘剩余空间跌至 **0 字节**，`%TEMP%` 下累计约 **8.5 GB** 的 `_MEI*` 目录（12 个），来源是被强杀的 onefile 实例未清理解压目录；清理后 C 盘恢复 9 GB 可用。
- **影响**：磁盘占满会导致 **EXE 启动失败**（onefile 解压失败）——本次实测中第二次启动即因此无日志、无进程存活，导致「持久化验证链不完整」，释放空间后重做才得到完整结论。
- **尚未确认的原因**：PyInstaller 对**被强杀的父进程**的 `_MEI` 清理行为。
- **状态**：**待验证风险 / 运维注意事项**，非产品代码缺陷。

### R-04 真实内网设备登录未验证

- **观测事实**：测试全部基于本地测试页与本地 mock server（`tests/test_server.py`）。
- **说明**：真实设备（`devices.json` 中的内网地址）当前不可达，**未验证**真实登录成功路径；**报告中不存在任何伪造的真实登录成功结果**。
- **状态**：**未验证项**，已在第 9 节明确标注。

### R-05 任务书「输入框命中但填写失败」的真实触发条件未完全定位

- **观测事实**：已确认 D-08 / D-09 / D-10 三条相邻缺陷（元素引用失效误分类、多匹配消歧失效、只读属性真值判断），均可导致「看起来命中了、实际填不进去」。
- **尚未确认的原因**：V5.0.6 现场日志没有记录**具体的失败分类**，无法判定当时命中的是哪一条。
- **状态**：**待验证风险**；三条缺陷已修复并有测试覆盖。

## 5. 默认模板的「修改 / 追加 / 刷新 / 持久化」机制

### 5.1 四类模板的边界（明确区分，互不混淆）

| 类别 | 位置 | 生命周期 | 谁可以改 |
|---|---|---|---|
| 内置初始模板 | `appcore/templates.py::PRESET_TEMPLATES` / `DEFAULT_TEMPLATE` | 只读常量，进程内不变 | 只能改代码 |
| 用户维护的默认模板文件 | EXE/项目同目录 `templates/default.json` | 跨进程持久 | 用户 / 程序 |
| 设备专属模板 | `templates/<设备模板名>.json` | 跨进程持久 | 用户 / 程序 |
| 模板管理器内存缓存 | `TemplateManager._templates` / `_sources` / `_errors` / `_file_errors` / `_loaded` / `_lock` | 进程内 | 只能经由管理器 API |

**关键约束**：
- 内置模板**只在文件缺失时**用于初始化（`create_default_template_files`）；
- `_MEIPASS`（PyInstaller 只读资源路径）与**用户可写配置路径**严格分离：用户模板始终位于 EXE 同目录的 `templates\`（可写），**不随包内置**；
- `_repair_preset_template` 只补齐「用户文件缺失 / 为空」的字段，且**跳过内置版本里本来就不存在的字段**（D-12）。

### 5.2 三种写入语义（追加 / 合并 / 主动替换）

| API | 语义 | 角色校验 | 确认 |
|---|---|---|---|
| `append_selectors_to_default(...)` | **只加新的**，原有选择器一条不动 | 不因模板原有内容里的冲突而阻塞追加 | 无需确认 |
| `merge_template_into_default(...)` | 按选择器值**合并**，同值不重复写入 | 同上 | 无需确认 |
| `replace_default_template(...)` | **整体替换**默认模板 | `strict_roles=True`：角色冲突直接拒绝，并指出具体字段与选择器 | 需要明确用户确认 |

- **保存前校验链**：JSON 语法 → 模板字段结构 → 元素角色 → 选择器结构；任一环节不通过则**不写盘**。
- **保存原子性**：`tempfile.mkstemp` + `os.replace`；保存失败**不破坏原文件**（`tests/test_config_refresh.py`「拒绝时默认模板文件未被破坏」）。
- **无法确认角色的选择器**不得直接作为有效用户名 / 密码选择器写入默认模板（D-11）。

### 5.3 刷新语义

`appui/main_window.py::on_refresh` 的完整流程：

```
快照当前模板缓存（template_snapshot）
  → TemplateManager.reload_templates(force=True)   # 强制重读磁盘，丢弃旧缓存
  → load_devices()                                  # 重新读取 devices.json
  → 校验新配置
      ├─ 成功：切换到新对象 + 重建设备列表/分组 UI
      └─ 失败：TemplateManager.restore_templates(template_snapshot)
                # 保留最后一次有效配置，不先清空再加载，允许改好后再刷新
```

- **生效范围**：**后续**登录任务使用新模板（`_resolve_template` 按登录尝试实时解析）；**运行中**已开始的浏览器任务不受影响（这一点在 UI 提示中说明）。
- 不存在「文件已更新但内存仍是旧对象」「缓存返回旧模板」「UI 刷了但登录任务仍用旧配置」「只刷设备不刷模板」中的任何一种。

### 5.4 持久化验证（打包态、离线、真实文件）

| 步骤 | 观测 | 结论 |
|---|---|---|
| 干净临时目录首次启动 EXE | 自动创建 `templates/default.json`（35 条用户名选择器）、`proxmox.json`、`huawei.json`、`app.log`、`login_logs.db` | 初始化正常 |
| 向 `default.json` 追加 `input#offline_probe_v510` | 文件内 36 条 | 追加成功 |
| **重启 EXE** | `default.json` 仍为 36 条，`input#offline_probe_v510` 保留 = **True** | **用户修改未被内置模板覆盖** |
| 重启日志 | **无**「预置模板不完整，已补齐缺失字段」告警；**无** WARNING / ERROR | D-12 修复生效 |
| 第二次启动耗时 | 97ms（首次 129ms） | 见第 8 节 |

## 7. 「用户名选择器已命中但随后填写失败」的真实原因

**结论：不是「命中后仍继续提交」的逻辑错误（该路径经核实不存在），而是三条相邻缺陷叠加。**

| # | 真实原因 | 根因 | 现象 | 修复 |
|---|---|---|---|---|
| 1 | **元素引用失效被误报为「不可见」** | Playwright ElementHandle 在 DOM 重渲染后 detached，`is_visible()` 抛异常被兜底成「不可见」 | 日志显示“元素不可见”，但真实原因是元素已失效，重试策略也用错 | `appcore/browser.py` 新增 `_is_detached`，`input_text_detailed` 增加 `element_detached` 归类（D-08） |
| 2 | **多匹配消歧失效，直接取第一个** | `quick_check_locator` 返回 `.first` | 页面上有多个同名输入框时，**未经验证**地填了第一个（可能是隐藏框/搜索框） | 返回完整 locator，多匹配判定为歧义、不给出发写元素（D-09） |
| 3 | **只读元素被判为可填写** | `get_attribute('readonly')` 对布尔属性返回**空字符串**，真值判断为 False | `fill()` 一直等到 30s 超时，表现为“卡住不填” | 改用 `is not None`；新增 `_fill_with_timeout`（D-10） |

**另有两条已排除的怀疑**：
- 「密码与按钮候选串用」→ 实测交集为空（D-06）；
- 「命中失败仍继续提交」→ `_locate_and_fill` 失败即 `return`，`_run_template_attempt` 直接返回失败（D-04）。

> ⚠️ **离线验证注意事项（R-03）**：onefile EXE 运行时会在 `%TEMP%` 解压约 250 MB 的 `_MEI*` 目录；**被强杀的实例不会清理它**。多次离线验证会累计占用系统盘（本次实测累计约 8.5 GB，曾导致 C 盘剩余 0 字节并使 EXE 启动失败）。验证结束后应清理：

> Get-ChildItem $env:TEMP -Directory -Filter "_MEI*" | ForEach-Object { Remove-Item $_.FullName -Recurse -Force -ErrorAction SilentlyContinue }
> ```
