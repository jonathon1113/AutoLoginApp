# AutoLoginApp-批量登录工具
适用于内网环境多设备自动登录的windown程序，使用python开发。

**一款面向网络运维与安全运维场景的 Windows 桌面批量登录工具。**

基于 Python、PyQt6 与 Playwright 开发，支持多设备分组管理、批量登录、快捷访问、个性化登录模板及选择器诊断，旨在减少日常运维中重复登录多个 Web 管理平台的时间成本。

如果你需要频繁登录防火墙、WAF、IPS、虚拟化平台、云平台及内部业务系统，希望这个项目能够帮助你把分散的登录操作集中管理起来。

## ✨ 项目亮点

- **集中管理**：通过桌面 GUI 统一管理多个 Web 管理入口。
- **批量操作**：减少逐台打开网页、填写凭据和切换标签页的重复工作。
- **配置驱动**：通过设备配置Excl表格导入和登录模板适配不同的管理页面。
- **定位诊断**：辅助检查页面元素和选择器，降低模板维护成本。
- **资源效率**：根据实际使用体验，本项目相较于此前采用 Selenium 的实现，内存占用更低；具体表现取决于设备数量、浏览器配置和测试环境。
- **Windows 桌面化**：可打包为可执行程序，降低日常使用门槛。

## 📌 为什么开发这个项目？

**最主要是在市面上没能找到类似的工具，所以决定手搓一个。**

在日常运维中，管理人员可能需要维护几十甚至上百个 Web 管理入口。每次工作都可能涉及打开浏览器、输入地址、填写账号密码、切换标签页等重复操作。

单独编写自动化脚本虽然能够解决部分问题，但设备数量增加后，脚本维护也会逐渐复杂：

- 不同厂商的登录页面存在差异，需要维护不同的元素定位规则。
- 页面改版后，原有选择器可能失效。
- 设备数量增加后，分散的脚本不利于统一管理。
- 依赖固定等待时间的脚本容易受到页面加载速度影响。
- 浏览器实例和标签页管理不当，可能增加内存开销。
- 登录失败时，缺少诊断信息会增加排查难度。

本项目希望将设备管理、登录任务、模板配置和故障诊断整合到一个桌面应用中，让批量登录更方便，也更容易维护。

## 🚀 核心优势

### 1. 多设备统一管理

不再需要为每台设备单独维护一份登录脚本。

- 支持设备分组管理。
- 支持批量发起登录任务。
- 支持常用设备快捷登录。
- 通过统一界面组织不同类型的 Web 管理入口。
- 通过配置文件维护设备信息，减少设备变更时的代码修改。

对于需要频繁访问不同厂商设备管理页面的网络运维和安全运维人员，这种集中管理方式可以减少重复劳动。

### 2. 配置驱动的登录模板

项目将设备信息与页面元素定位规则分开管理，降低新增设备的适配成本。

- 支持默认模板与设备专用模板。
- 支持用户名、密码、登录按钮等元素的定位规则配置。
- 支持多个候选选择器，适应不同页面结构。
- 支持模板生成、校验、保存和更新等维护流程。
- 尽可能复用已有模板，减少重复编写代码。

相比为每个网站维护独立脚本，这种方式更适合需要持续增加和维护设备的场景。

### 3. 选择器校验与故障诊断

自动化登录不只是找到一个输入框，还需要确认目标元素是否符合预期。

项目围绕元素定位和登录流程提供辅助诊断能力：

- 检查选择器能否定位到目标元素。
- 辅助识别用户名输入框、密码输入框和登录按钮。
- 记录定位阶段、候选选择器和失败原因。
- 通过受控等待减少对固定 `sleep` 的依赖。
- 在模板失效或页面变化时，为排查问题提供线索。

这些机制旨在提高登录任务的可诊断性，但不能保证所有厂商页面都能一次适配成功。

### 4. 内存占用与资源管理

**资源占用也是桌面自动化工具的重要评价指标。**

对于需要同时管理多个设备的场景，除了登录速度，内存占用同样会影响工具的使用体验。

根据本项目的实际使用观察，与此前采用 Selenium 的实现相比，本项目的运行内存占用明显更低。这对于需要长时间运行、同时管理多个设备页面的运维场景具有实际意义。

可能影响两种实现内存差异的因素包括：

- **浏览器实例管理**：是否复用已有浏览器实例，而不是为每台设备重复启动完整浏览器。
- **标签页管理**：是否合理组织设备页面，避免不必要的标签页和重复页面。
- **运行时开销**：Python 自动化框架及其相关组件自身的资源消耗。
- **页面资源**：网页中的 JavaScript、图片、动态组件和后台任务。
- **生命周期管理**：是否及时释放不再使用的页面、上下文和浏览器资源。

需要说明的是，内存占用并非仅由 Playwright 或 Selenium 决定。两者的实际差异与实现方式密切相关，不能仅凭框架名称判断优劣。

本项目更关注的是：在满足多设备登录需求的前提下，尽可能控制不必要的资源开销，改善实际使用体验。

### 5. 为什么选择 Playwright，而不是 Selenium？

本项目选择 Playwright，主要基于当前项目的浏览器自动化需求、页面操作方式和代码维护目标。

| 对比维度 | Playwright（本项目采用） | Selenium |
|---|---|---|
| 页面等待 | 内置自动等待和可操作性检查，减少部分手动等待代码 | 支持显式等待和 Expected Conditions，同样可以实现可靠等待 |
| 元素定位 | 提供 Locator API 和多种定位策略 | 支持 CSS、XPath 等成熟定位方式 |
| 多标签页管理 | 提供 Page、BrowserContext 等对象模型 | 支持多窗口、多标签页及会话管理 |
| iframe | 提供 FrameLocator 等操作方式 | 支持切换 iframe 并操作内部元素 |
| 浏览器驱动管理 | 提供集成度较高的浏览器安装与管理机制 | 常见方案使用 WebDriver，现代 Selenium 也可通过 Selenium Manager 简化驱动管理 |
| 内存占用 | 取决于具体实现；本项目实际使用中观察到占用较低 | 同样取决于浏览器实例、页面数量和实现方式 |
| 生态与兼容性 | 适合现代 Web 自动化，API 设计较统一 | 生态成熟、语言支持广泛，适合既有自动化体系 |

#### 选择 Playwright 的主要原因

- **更简洁的等待逻辑**：自动等待机制能够处理许多常见的元素就绪和可操作性检查，减少手动编写等待代码的工作量。
- **统一的页面操作接口**：通过页面、浏览器上下文和定位器等 API 组织浏览器操作。
- **适应动态页面**：便于处理动态加载的页面、多标签页和 iframe 等场景。
- **适合当前技术架构**：结合 Python 和 PyQt6，可以将浏览器自动化、设备管理、运行日志及桌面交互整合到一个应用中。
- **实际使用中的资源表现**：本项目观察到的内存占用低于此前的 Selenium 实现，但这属于具体项目的使用结果，并不代表 Playwright 在所有场景下都更省内存。

#### 为什么不直接使用 Selenium？

并不是 Selenium 无法实现这些功能。

Selenium 同样可以完成批量登录、元素定位、多窗口管理和异常处理，也有成熟的生态与广泛的应用基础。

本项目选择 Playwright，是为了更贴合当前的技术架构和维护目标。如果你已经拥有成熟的 Selenium 自动化体系，或者依赖特定的 WebDriver 工作流，继续使用 Selenium 可能更合适。

**本项目的价值不在于否定 Selenium，而在于通过合适的技术组合，解决多设备登录管理这一具体问题。**

### 6. 图形界面与 Windows 部署

项目使用 PyQt6 构建桌面界面，将设备管理、登录操作和运行日志整合到同一个应用中。

- 无需每次手动运行独立 Python 脚本。
- 通过图形界面组织设备并执行常用操作。
- 通过日志观察执行过程和排查问题。
- 可使用 PyInstaller 打包为 Windows 可执行程序。

对于不希望直接维护浏览器自动化代码的运维人员，图形界面能够降低日常使用门槛。

## ⚖️ 项目的不足与局限

一个实用的开源项目不仅应该说明优势，也应该明确它的适用边界。

### 1. 不能保证所有设备都能直接适配

不同厂商的登录页面存在较大差异。部分设备使用标准 HTML 表单，另一些可能使用复杂的 JavaScript、自定义组件、iframe 或特殊认证流程。

对于不兼容的页面，用户可能仍然需要分析页面结构、调整选择器或维护专用模板。

### 2. 验证码、多因素认证和单点登录存在限制

验证码、短信验证、硬件令牌、多因素认证（MFA）、单点登录（SSO）以及动态认证策略可能需要人工操作或专项适配。

因此，本项目不应被理解为能够自动处理所有认证流程的工具。

### 3. 内存占用优势需要结合具体环境理解

虽然本项目实际使用中观察到内存占用低于此前的 Selenium 实现，但这一结果不能直接推广到所有 Playwright 和 Selenium 项目。

- 同时打开的页面越多，浏览器的内存需求通常越高。
- 复杂页面、持续运行的 JavaScript 和后台任务可能显著增加内存占用。
- 不同浏览器版本、启动参数和运行环境可能产生不同结果。
- 如果两种实现的浏览器实例数量和页面数量不同，直接比较内存数值可能不公平。

更严谨的比较应使用相同的设备页面、浏览器版本和登录流程，并在相同测试时段测量所有相关进程的内存占用。

### 4. Playwright 并非零依赖方案

即使将程序打包为 Windows 可执行文件，浏览器自动化环境仍需要维护。

- 打包文件可能较大，特别是在包含浏览器运行组件时。
- Playwright 版本与浏览器版本需要保持兼容。
- 更新依赖或排查浏览器启动问题仍需要一定的技术基础。
- 不同 Windows 环境及安全策略可能影响运行结果。

如果只需要自动化一个简单网页，轻量级脚本可能更简单。本项目主要面向多个设备的集中管理需求。

### 5. 页面变化仍可能导致登录失败

自动等待机制不能完全消除自动化错误。

例如，页面改版、选择器失效、元素匹配不唯一、组件动态加载或登录流程改变，都可能导致任务失败。

模板化配置和诊断日志能够帮助降低维护成本，但不能保证长期免维护。

### 6. 不是完整的运维自动化平台

本项目主要用于 Web 管理页面的登录和访问，不等同于完整的资产管理系统、配置管理平台、统一身份认证系统或远程命令执行平台。

如果需要大规模资产发现、配置下发、命令执行和集中审计，可能还需要结合其他专业工具。

### 7. 账号凭据需要妥善保护

自动化登录涉及敏感设备账号。

用户应根据实际使用方式评估凭据保存、文件访问权限、日志输出和备份风险。不要将真实账号密码、令牌、内部地址或生产环境配置提交到公开仓库。
